# Руководство пользователя

Решение WindAgent выпускает почасовой прогноз выработки двух турбин ВЭС на 24–48 часов вперёд. Документ описывает установку, команды, формат результатов и разбор типичных ошибок.

Для кого: диспетчер ВЭС или сотрудник энергосбыта, который формирует суточный график выработки для заявок на рынок и планирования резервов; инженер, который воспроизводит расчёт и проверяет качество.

Что закрывает: для каждой даты выпуска агент сам берёт архивный прогноз погоды, доступный именно на эту дату, готовит признаки, считает прогноз по каждой турбине, анализирует результат, при необходимости пересчитывает и сохраняет выпуск вместе с журналом действий. Фактическая погода не используется нигде.

## Требования

| Компонент | Значение |
|---|---|
| Python | 3.10 и новее; проверено на 3.14 (Windows 11) и 3.11 (образ Docker) |
| Диск | ~200 МБ: данные кейса 12 МБ, кэш прогнозов 6.2 МБ, обученные модели 8 МБ, зависимости |
| Сеть | нужна только при первой установке зависимостей; расчёт идёт из кэша `data/cache/weather/` |
| Ключ LLM | не обязателен: без ключа агент работает по детерминированному плану |

### Linux и macOS

```bash
git clone https://github.com/BAITC-Hacks/hack-c63c1350-technokod.git
cd hack-c63c1350-technokod
python3 -m venv .venv
source .venv/bin/activate

```

Время шагов на рабочей машине (Windows 11, Python 3.14): создание окружения — несколько секунд, `pip install -r requirements.txt` — 1–2 минуты, `check` — единицы секунд, обучение моделей — около 15 секунд.

Дальше в примерах используется `.venv\Scripts\python.exe` (Windows). В Linux и macOS подставляйте `.venv/bin/python`. Если окружение активировано (`Activate.ps1` или `source`), достаточно `python`.

Ключ LLM (не обязателен) задаётся в `.env`:

```
LLM_PROVIDER=openai
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-5.4-mini
OPENAI_REASONING_MODEL=gpt-5.4
DEMO_MODE=false
```

Файл `.env` в `.gitignore` и в репозиторий не попадает. Без ключа команды работают, LLM-оркестрация заменяется детерминированным планом.

## Быстрый старт

```powershell
powershell -ExecutionPolicy Bypass -File scripts\demo.ps1     # Windows
bash scripts/demo.sh                                          # Linux, macOS
```

Скрипты сами выбирают интерпретатор: переменная `PYTHON`, если она задана, затем `.venv` проекта, затем `python` из PATH — и печатают выбранный. Переопределить можно так: `$env:PYTHON=".venv\Scripts\python.exe"` в PowerShell, `PYTHON=.venv/bin/python bash scripts/demo.sh` в Linux и macOS.

Сценарий из семи шагов: проверка окружения → обучение (пропускается, если модели уже есть) → выпуск прогноза на одну дату → бэктест февраля 2026 → сводка → автотесты → живая LLM-оркестрация. Последний шаг выполняется только при заданном ключе, без ключа он пропускается с сообщением. Сеть не нужна, ключи не обязательны. Любая ошибка останавливает сценарий с ненулевым кодом возврата.

На свежем клоне перед демонстрацией нужно один раз обучить модели — файлы `models/*.joblib` в репозитории не хранятся:

```powershell
.venv\Scripts\python.exe -m app.cli train
```

Обучение занимает около 15 секунд. На уже обученных моделях весь контрольный сценарий из семи шагов проходит за 20 секунд (замер на рабочей машине).

Проверка окружения отдельной командой даёт такой вывод (пример с рабочей машины):

## Команды

Общий вид: `python -m app.cli <команда> [аргументы]`. Флаги `--llm` и `--no-llm` доступны у `forecast` и `backtest`: без флага агент включает модель, если ключ задан; `--no-llm` принудительно оставляет детерминированный план; `--llm` требует LLM.

### check — проверка окружения

```powershell
.venv\Scripts\python.exe -m app.cli check
```

Печатает версию Python, каталог проекта, наличие данных по каждой турбине, обучены ли модели, сколько файлов в кэше погоды и возможен ли прогон без сети, провайдера LLM и задан ли ключ (сам ключ не печатается), версии pandas и scikit-learn. Файлы не создаёт. Выполняйте после установки и при любой непонятной ошибке.

### fetch-weather — прогрев кэша архивных прогнозов

```powershell
.venv\Scripts\python.exe -m app.cli fetch-weather --start 2026-01-29 --end 2026-03-01
```

Запрашивает у Open-Meteo архивные прогнозы на интервал и складывает ответы в `data/cache/weather/*.json`. Нужна сеть. Для тестового периода кэш уже лежит в репозитории, команда требуется только при расширении диапазона дат.

### train — обучение моделей

```powershell
.venv\Scripts\python.exe -m app.cli train
```

Обучает модель по каждой турбине на истории выработки и архивных прогнозах, проводит честную валидацию на январе 2026, подбирает веса смеси и дообучает финальную модель на всех данных. Занимает около 15 секунд. Создаёт `models/turbine_1.joblib`, `models/turbine_2.joblib` и обновляет `docs/metrics.json`. Печатает по строке на турбину с весами смеси и ошибкой на горизонтах 24 и 48 часов.

### forecast — выпуск прогноза на одну дату

```powershell
.venv\Scripts\python.exe -m app.cli forecast --date 2026-01-31 --no-llm
.venv\Scripts\python.exe -m app.cli forecast --date 2026-02-06 --horizon 48
```

Аргументы: `--date` (дата выпуска, обязательный), `--horizon` (часы, по умолчанию 48), `--llm` / `--no-llm`.

Дата выпуска — это день, на который берётся прогноз погоды. Горизонт начинается со следующих суток: выпуск от 31.01 покрывает 01.02 (первые 24 часа, прогноз суточной давности) и 02.02 (вторые 24 часа, прогноз двухсуточной давности). Бэктест начинается с 29.01, поэтому часы 31 января тоже закрыты обоими горизонтами, а 01.02 получает и суточный, и двухсуточный прогноз.

Вывод (числа зависят от даты):

```
выпуск прогноза 2026-01-31, горизонт 48 ч
трасса инструментов: get_weather → check_input_quality → prepare_and_predict → analyze → save_forecast
анализ: {"calm_hours": ..., "rated_hours": ..., "storm_hours": ..., "needs_recalculation": false, ...}
заключение: Выпуск 2026-01-31, горизонт 48 ч. ...
файлы: outputs/forecasts/2026-01-31.csv, outputs/agent_logs/2026-01-31.json
```

Создаёт `outputs/forecasts/<дата>.csv` (96 строк: 48 часов × 2 турбины) и `outputs/agent_logs/<дата>.json`.

### backtest — все выпуски тестового периода

```powershell
.venv\Scripts\python.exe -m app.cli backtest --no-llm
.venv\Scripts\python.exe -m app.cli backtest --start 2026-02-10 --end 2026-02-14 --no-llm
```

Прогоняет выпуски подряд с 29.01 по 27.02.2026 (30 выпусков). Каждый следующий выпуск видит предыдущий, поэтому агент сравнивает пересекающиеся часы и решает, нужен ли пересчёт. По каждому дню печатается строка с числом часов и средней мощностью по турбинам, в конце — сводка: сколько выпусков, сколько строк, сколько часов февраля собрано, есть ли пропуски, в какие дни был пересчёт.

Создаёт `outputs/forecast_all_issues.csv`, `outputs/forecast_feb2026.csv`, `outputs/backtest_summary.csv`, `outputs/backtest_summary.json`, а также по файлу выпуска и журналу на каждый день.

### report — сводка по посчитанному

```powershell
.venv\Scripts\python.exe -m app.cli report
```

Печатает качество модели на честной валидации из `docs/metrics.json` (MAE, RMSE, nMAE на горизонтах 24 и 48 часов по каждой турбине), число выпусков и пересчётов, число часов февраля и пропусков, среднюю ожидаемую мощность по турбинам и суточный профиль по ВЭС. Файлы не изменяет. Если бэктест ещё не запускался, подсказывает нужную команду.

## HTTP-сервис

Для интеграции с системами диспетчера тот же агент доступен по HTTP:

```powershell
.venv\Scripts\python.exe -m app.serve
```

Адрес и порт берутся из `.env` (`APP_HOST`, `APP_PORT`), по умолчанию `0.0.0.0:8000`. Интерактивная документация — `http://localhost:8000/docs`.

| Запрос | Что делает |
|---|---|
| `GET /health` | состояние сервиса: обучены ли модели, какой провайдер LLM |
| `GET /forecast/{issue_date}?horizon=48&llm=false` | выпуск прогноза агентом на дату: трасса инструментов, анализ, признак пересчёта, заключение и почасовые значения (`ts`, `lead_day`, `turbine`, `power_norm_pred`, `power_p10`, `power_p90`) |
| `GET /submission` | итоговый почасовой ряд февраля из `outputs/forecast_feb2026.csv` |

Горизонт принимает только 24 или 48. Если модели не обучены, `/forecast` отвечает кодом 503 с подсказкой; если бэктест не запускался, `/submission` отвечает 404. Запрос к `/forecast` выполняет полный цикл агента и, как и команда CLI, записывает файлы выпуска и журнал.

## Выходные файлы

Все значения мощности нормированы на номинал турбины и лежат в диапазоне 0..1. Время местное (Asia/Almaty), шаг один час, метка времени — начало часа.

### outputs/forecasts/&lt;дата&gt;.csv — один выпуск

| Колонка | Смысл |
|---|---|
| `issue_date` | дата выпуска: прогноз погоды взят таким, каким он был доступен на эту дату |
| `ts` | час прогноза, местное время |
| `horizon_hour` | номер часа горизонта, 1..48 |
| `lead_day` | 1 — прогноз суточной давности (часы 1–24), 2 — двухсуточной (часы 25–48) |
| `turbine` | номер турбины, 1 или 2 |
| `wind_speed_100m` | прогнозная скорость ветра на высоте 100 м, м/с — вход, по которому считался прогноз |
| `power_norm_pred` | итоговый прогноз выработки, доля номинала 0..1 |
| `power_p10`, `power_p90` | нижняя и верхняя границы интервала неопределённости |
| `power_gbm_pred` | компонента градиентного бустинга (вес в смеси нулевой, оставлена для сравнения) |
| `power_two_stage_pred` | компонента двухэтапной схемы: прогноз скорости на гондоле → измеренная кривая турбины |
| `power_curve_pred` | компонента эмпирической кривой мощности |
| `wind_nacelle_pred` | промежуточный выход двухэтапной схемы: прогнозная скорость ветра на гондоле, м/с |

В файле 96 строк (48 часов × 2 турбины) и 13 колонок в этом порядке — он задан константой
`FORECAST_COLUMNS` в `app/agent.py`. Значения округлены до четырёх знаков.

### outputs/agent_logs/&lt;дата&gt;.json — журнал выпуска

Ключи: `issue_date`, `llm_used` (порядок инструментов выбирала LLM), `published` (был ли выпуск опубликован), `confidence` (достоверность: обычная либо пониженная при вердикте `warn`), `quality` (вердикт контроля качества входа, число полученных часов и перечень находок), `recalculated` (был ли пересчёт), `analysis` (числа проверки: часы штиля, номинала и шторма, разброс между турбинами, средний КИУМ, изменение относительно вчерашнего выпуска, действующий порог, доступность вчерашнего выпуска и признак необходимости пересчёта), `conclusion` (текст для диспетчера), `trace` (последовательность вызванных инструментов с их результатами; запись `llm_fallback` означает, что оркестрация откатилась на детерминированный план). По журналу проверяется, что выпуск прошёл полный цикл, что использовался только архивный прогноз и что вход прошёл контроль качества.

Если вердикт контроля равен `fail`, выпуска не будет: в журнале `published: false`, а в заключении перечислено, что именно не так со входными данными. Это штатное поведение, а не сбой: прогноз по негодным данным внешне неотличим от нормального, поэтому агент отказывается его публиковать.

Рядом лежит `outputs/agent_logs_llm/` — три выпуска (05.02, 15.02, 21.02), где порядок инструментов выбирала модель. В двух из них она сама распознала обновление входных данных и вызвала пересчёт.

### outputs/forecast_feb2026.csv — итоговый ряд февраля

Одна строка на час с 01.02.2026 00:00 по 28.02.2026 23:00, всего 672 строки без пропусков.

| Колонка | Смысл |
|---|---|
| `ts` | час, местное время |
| `turbine_1_lead1`, `turbine_2_lead1` | прогноз, выпущенный за сутки до этого часа (основной результат) |
| `turbine_1_lead2`, `turbine_2_lead2` | прогноз, выпущенный за двое суток |
| `turbine_1_p10`, `turbine_2_p10`, `turbine_1_p90`, `turbine_2_p90` | границы интервала неопределённости для свежайшего выпуска |
| `farm_mean_lead1`, `farm_mean_lead2` | станция целиком: среднее долей номинала двух турбин, на сутки и на двое суток |
| `farm_p10_lead1`, `farm_p90_lead1` | границы интервала по станции для свежайшего выпуска |

Всего 13 колонок, пропусков нет ни в одной: выпуски начинаются с 29 января, поэтому каждый час февраля закрыт обоими горизонтами.

### outputs/forecast_all_issues.csv — все выпуски целиком

Те же колонки, что в файле одного выпуска, но за все 30 дат: 2 880 строк. Нужен для разбора, как менялся прогноз на один и тот же час по мере приближения.

### outputs/backtest_summary.csv — по строке на выпуск

`issue_date`, `hours`, `recomputed`, `llm_used`, `storm_hours`, `calm_hours`, `rated_hours`, `mean_cf_t1`, `mean_cf_t2`, `mean_abs_change_vs_prev`. Рядом лежит `backtest_summary.json` с теми же строками плюс заключение агента и список вызванных инструментов.

### Перевод в МВт·ч

Значения нормированы, номинальная мощность турбины в данных кейса не выдана. Энергия за период считается так:

```
E (МВт·ч) = Σ power_norm(h) × P_ном (МВт) × 1 ч
```

Например, сумма `power_norm_pred` по 24 часам, умноженная на паспортную мощность турбины, даёт суточную выработку. Колонка `farm_mean_lead1`, умноженная на суммарную мощность ВЭС, даёт среднюю мощность станции в этот час.

## Типовые сценарии

**Прогноз на завтра.** Дата выпуска — сегодня:

```powershell
.venv\Scripts\python.exe -m app.cli forecast --date 2026-02-10
```

Первые 24 часа файла — завтрашние сутки, вторые 24 — послезавтрашние.

**Пересчёт после обновления прогноза погоды.** Запустите ту же команду для той же даты повторно: агент заново берёт входные данные, сравнивает с предыдущим выпуском и, если среднее изменение превысило порог 0.15 или появились штормовые часы, пересчитывает прогноз и отмечает это в журнале (`recalculated: true`). Файл выпуска перезаписывается.

**Проверить, что было в конкретный день.** Откройте `outputs/agent_logs/<дата>.json`: там трасса инструментов, числа анализа и заключение. Сам прогноз — в `outputs/forecasts/<дата>.csv`.

**Прогнать весь февраль.** `backtest --no-llm`, затем `report`. Итог для сдачи — `outputs/forecast_feb2026.csv`.

## Частые ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `Модели не обучены. Выполните: python -m app.cli train` | нет файлов `models/*.joblib`, они не хранятся в репозитории | выполнить `train` (около 15 секунд) |
| `архив прогнозов на <дата> пуст` | запрошена дата вне кэша и нет сети, либо дата вне покрытия архива (Previous Runs начинается с 16.02.2024) | прогреть кэш `fetch-weather` при наличии сети или взять дату внутри тестового периода |
| Агент не обращается к LLM, хотя ключ есть | `DEMO_MODE=true` в `.env`, либо указан `--no-llm`, либо провайдер в `LLM_PROVIDER` не совпадает с заданным ключом | проверить `check`, привести `.env` в порядок |
| Ошибка провайдера LLM во время выпуска | нет сети, исчерпан лимит, неверный ключ | ничего не требуется: агент сам откатывается на детерминированный план, в трассе появляется `llm_fallback` с причиной |
| `httpx.ConnectError` при первом запуске на новой машине | холодный кэш и нет сети | выполнить `fetch-weather` при наличии сети; для тестового периода кэш уже в репозитории |
| Кракозябры в выводе PowerShell или cmd | консоль Windows в кодировке cp866 | `chcp 65001` перед запуском либо запуск в Windows Terminal |
| `ModuleNotFoundError: app` | команда запущена не из корня проекта | перейти в каталог репозитория и повторить |
| Конфликт версий при установке | системный Python старше 3.10 или установка идёт мимо venv | создать окружение заново на Python 3.10+, убедиться, что используется `.venv\Scripts\python.exe` |
| Файл `.env` не найден при запуске через Docker | `docker-compose.yml` требует `.env` | создать файл из `.env.example` (можно оставить пустой ключ) |
