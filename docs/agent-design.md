# Устройство агентного контура

Модуль `app/agent.py`. Здесь описано, что именно делает агент, какими инструментами, по каким порогам
принимает решения и что остаётся в журнале для проверки.

## Почему это агент, а не скрипт

Скрипт выполняет фиксированную цепочку вызовов. Агент здесь отличается тремя свойствами:

1. **Наблюдение и решение.** После расчёта прогноз не отдаётся сразу: инструмент `analyze` измеряет
   состояние выпуска (штиль, номинал, шторм, расхождение турбин, отличие от вчерашнего выпуска) и выдаёт
   вердикт `needs_recalculation`. Решение о пересчёте принимается по этому наблюдению, а не по расписанию.
2. **Действие по результату проверки.** При срабатывании условия агент сам вызывает `recalculate`:
   заново опрашивает источник прогноза, пересчитывает выработку и применяет защитный останов — то есть
   действует по итогу собственной проверки, а не по расписанию.
3. **Выбор порядка действий.** Когда доступна LLM, последовательность инструментов выбирает модель через
   function calling, а не жёсткий код. Набор инструментов при этом один и тот же в обоих режимах, поэтому
   результат остаётся проверяемым.
4. **Отказ от действия.** Инструмент `check_input_quality` проверяет полученные данные до расчёта, и при
   вердикте `fail` выпуск не публикуется вовсе. Это единственное свойство из четырёх, которое даёт
   измеримое расхождение с жёстким конвейером: на шести деградациях входа конвейер публикует все шесть
   молча, агент отказывает в четырёх и ловит аномалию пересчётом в пятой
   (`scripts/degradation_experiment.py`, разбор в [`root-analysis/03-agency.md`](root-analysis/03-agency.md)).
   Остальные три свойства в ретроспективном прогоне по архиву вырождаются: источник на прошедшую дату
   всегда возвращает один и тот же срез, поэтому пересчёт не меняет чисел.

Цикл одного выпуска:

```
наблюдение            проверка входа          действие               проверка            решение
get_weather ──► check_input_quality ──► prepare_and_predict ──► analyze ──► needs_recalculation?
                     │ fail
                     ▼
              выпуск не публикуется
                                                       │           │ да
                                                       │ нет       ▼
                                                       │     recalculate
                                                       │     (внутри снова prepare_and_predict
                                                       │      и буревое обнуление)
                                                       ▼           │
                                                 save_forecast ◄───┘  → CSV выпуска + журнал JSON
```

**Критерии остановки.** Цикл ограничен `max_steps = 10` обменами с моделью (параметр конструктора).
Выпуск считается состоявшимся только после `save_forecast`. Если модель закончила диалог, не вызвав
`analyze` или `save_forecast`, это делает страховка в `run_day`, поэтому неполных выпусков не бывает.
Зацикливание пересчёта исключено: `recalculate` вызывает `prepare_and_predict`, но не сам себя и не
`analyze`.

## Инструменты

Пороги заданы константами в начале `app/agent.py`: `CUT_IN = 3.0`, `RATED = 11.5`, `STORM = 22.0`,
`UPDATE_THRESHOLD = 0.15`, и отдельно пороги контроля входа: `MAX_WIND = 40.0`, `MIN_TEMP = -60.0`,
`MAX_TEMP = 60.0`, `STUCK_HOURS = 6`, `MIN_WIND_STD = 0.3`. Пороги скорости ветра согласованы с кривой
мощности из `docs/analysis.md` (нулевая выработка до 3 м/с, полка с 11–12 м/с); пороги контроля входа —
с физикой площадки (максимум за всю историю около 23 м/с) и климатом Казахстана.

### `get_weather(issue_date?)`

Забирает архивный прогноз на 48 часов по координатам ВЭС, каким он был доступен на дату выпуска
(`forecast_available_at`). Аргумент `issue_date` необязателен, по умолчанию — дата текущего выпуска.

Возвращает: число часов, границы периода, сколько часов пришло из слоя за сутки (`lead1_hours`) и за
двое суток (`lead2_hours`), min/mean/max скорости ветра на 100 м, min/max температуры и подпись
источника «Open-Meteo Previous Runs, выпуск не позже даты прогноза». Кадр погоды остаётся в состоянии
агента. Отказ источника поднимается исключением и перехватывается оркестратором.

### `check_input_quality()`

Проверяет погодный кадр до расчёта. Смысл проверки в том, что прогноз по испорченному входу внешне
неотличим от исправного: модель послушно посчитает выработку по застрявшему датчику или по обрезанному
ряду и выдаст правдоподобные числа.

Что проверяется: полнота горизонта (получено часов меньше запрошенных), непрерывность часовой сетки,
пропуски в скорости ветра и температуре, отрицательная скорость, значения выше физического предела
`MAX_WIND`, застрявшее значение (серия одинаковых отсчётов длиной от `STUCK_HOURS`), подозрительно
ровный ряд (разброс ниже `MIN_WIND_STD`), температура вне `MIN_TEMP…MAX_TEMP`.

Вердикт — худший из уровней находок: `fail` останавливает выпуск, `warn` публикует его с пониженной
достоверностью, `ok` не ограничивает ничего. Возвращает `verdict`, `hours`, `expected_hours`,
`publish_allowed` и список `findings`, где у каждой находки есть `level`, `code`, `message` и числовые
подробности. При `fail` детерминированный план прекращает выпуск сразу после этого шага и пишет
заключение с перечнем проблем, а `save_forecast` отказывается писать файл даже при прямом вызове.

Чего проверка не ловит принципиально: равномерный сдвиг всего поля ветра — он физически правдоподобен
и не отличим от настоящей смены погодной обстановки. Такой случай перехватывает второй слой — сравнение
с выпуском предыдущего дня в `analyze`.

### `prepare_and_predict()`

Строит признаки и считает прогноз по каждой турбине моделью из `models/turbine_*.joblib`. Модели
читаются один раз при создании агента, поэтому бэктест прогоняет 30 выпусков без повторного чтения с
диска. Здесь же в выпуск проставляются `issue_date`, `horizon_hour` и прогнозная скорость ветра.

Возвращает: число часов (`hours`), число строк (`rows`), средний КИУМ по турбинам (`mean_cf`) и
суммарную нормированную выработку за горизонт (`energy_norm_h`, норм·ч). Без предварительного
`get_weather` возвращает `{"error": …}` и ничего не считает.

### `analyze()`

Считает состояние выпуска:

| Поле | Смысл |
|---|---|
| `calm_hours` | часов с ветром ниже 3 м/с — выработки не будет |
| `rated_hours` | часов с ветром от 11.5 м/с — полка номинальной мощности |
| `storm_hours` | часов с ветром от 22 м/с — риск защитного останова |
| `turbine_spread_max` | максимальное расхождение прогнозов двух турбин в один час |
| `mean_cf` | средний КИУМ по турбинам, ключи «1» и «2» |
| `input_update_vs_previous_issue` | сравнение со вчерашним выпуском: `overlap_hours` (обычно 24), `mean_abs_change`, `max_abs_change` |
| `input_change_vs_previous_issue` | то же среднее изменение отдельным числом, для сводки бэктеста |
| `update_threshold` | действующий порог 0.15 — решение читается по журналу без обращения к коду |
| `needs_recalculation` | `storm_hours > 0` или среднее изменение выше порога |

Если предыдущего выпуска нет (первый день периода), поля сравнения пустые, и это честно попадает в
заключение.

### `recalculate(reason?)`

Вызывается, когда анализ дал `needs_recalculation`: в детерминированном плане — автоматически, в режиме
оркестрации — по решению модели. Заново опрашивает источник прогноза на ту же дату выпуска,
пересчитывает выработку через `prepare_and_predict` и обнуляет часы с ветром от 22 м/с — по всем
колонкам `power_*`, а не только по итоговой, иначе компоненты смеси противоречили бы результату.

Возвращает числовой триггер вместо общей фразы: `trigger` (`storm_hours`, `input_update`,
`quality_warn` или `manual`), человекочитаемый `trigger_detail` вида «расхождение с выпуском 2026-02-14
равно 0.164 при пороге 0.15», `trigger_values` с самими числами, `reason_passed` — формулировку,
переданную вызывающей стороной (в режиме оркестрации это слова модели), а также `input_changed`,
`storm_hours`, `rows_zeroed` и пояснение `note`. Поле `input_changed` нужно для честности: в бэктесте
по архиву повторный запрос возвращает тот же срез, `input_changed` всегда `false`, и `note` прямо
объясняет почему — в промышленном режиме здесь был бы новый выпуск прогноза погоды.

### `save_forecast()`

Пишет `outputs/forecasts/<issue_date>.csv` — 96 строк (48 часов × 2 турбины), 13 колонок
`FORECAST_COLUMNS`, значения округлены до четырёх знаков — и возвращает путь и число строк. Журнал
`outputs/agent_logs/<issue_date>.json` пишется в конце выпуска (`_write_log`), когда готово заключение:
оно появляется только после последнего обмена с моделью.

## Оркестрация моделью

Схемы инструментов собираются в `_run_with_llm` в формате OpenAI function calling
(`{"type": "function", "function": {"name", "description", "parameters"}}`). Обмен идёт через
`app.llm.chat_tools`, который возвращает единый словарь `{"content", "tool_calls"}` независимо от версии
SDK, поэтому агент не зависит от формы ответа провайдера.

Системный промпт задаёт:

- роль: агент-диспетчер ВЭС из двух турбин, Шелекский коридор;
- задачу: выпустить почасовой прогноз на 24–48 часов для названной даты выпуска;
- запрет на фактическую погоду: только `get_weather`, то есть архивный прогноз на дату выпуска;
- обязательный полный цикл и обязательный вызов `save_forecast` — до него прогноз не выпущен;
- правило пересчёта: при штормовых часах или изменении входных данных вызвать `recalculate`;
- формат заключения: 3–5 предложений по-русски, без разметки, для диспетчера.

Обработка ошибок и лимитов: каждый вызов инструмента обёрнут в `try/except`, ошибка возвращается модели
как `{"error": …}` и не роняет выпуск — модель исправляется следующим вызовом, например вызывает
`get_weather` перед расчётом. Сбой самого провайдера — нет ключа, сеть, лимит, некорректный ответ —
перехватывается в `run_day`: в трассу добавляется `llm_fallback` с текстом ошибки, и выпуск целиком
переигрывается детерминированным планом, который проходит цикл заново с первого инструмента.

**Режим без ключа.** `llm.available()` проверяет провайдера и `DEMO_MODE`; при `use_llm=None` агент сам
решает, доступна ли оркестрация. Детерминированный план выполняет те же шесть инструментов в фиксированном
порядке, а заключение собирает из тех же чисел анализа. Поэтому жюри получает
идентичный по структуре результат без ключей и без сети.

## Обнаружение обновления входных данных

Сравниваются пересекающиеся часы соседних выпусков: часы 25–48 вчерашнего выпуска — это часы 1–24
сегодняшнего, и они посчитаны по разным прогнозам погоды (слой за двое суток против слоя за сутки).
Среднее абсолютное изменение прогноза мощности на этих часах — прямая мера того, насколько обновился
вход. Порог 0.15 по нормированной мощности означает смену режима, а не шум уточнения.

Предыдущий выпуск передаётся в `run_day(issue_date, previous=...)`; если не передан, агент читает
вчерашний CSV с диска. Штормовые часы обрабатываются отдельно от порога: при ветре от 22 м/с
соответствующие часы обнуляются, потому что турбина уходит в защитный останов и модель кривой мощности
там неприменима (в обучающей истории таких режимов нет — максимум 23 м/с по датчику гондолы).

## Журнал действий

`outputs/agent_logs/<дата>.json`:

```json
{
  "issue_date": "2026-02-05",
  "llm_used": true,
  "published": true,
  "confidence": "обычная",
  "quality": { "verdict": "ok", "hours": 48, "expected_hours": 48, "findings": [], "publish_allowed": true },
  "recalculated": false,
  "analysis": { "calm_hours": 8, "rated_hours": 8, "storm_hours": 0, "update_threshold": 0.15,
                "previous_issue_available": true, "previous_issue_source": "передан бэктестом", "…": "…" },
  "conclusion": "Прогноз выпущен на 48 часов для турбин 1 и 2. …",
  "trace": [ { "tool": "get_weather", "result": { "hours": 48, "…": "…" } } ]
}
```

По журналу проверяется главное требование кейса: в трассе видно, что погода получена инструментом
`get_weather` с подписью источника «прогноз, доступный к концу суток выпуска», а не из факта; видно, какие
решения принял агент, был ли пересчёт и по какой причине, и вызвал ли оркестратор LLM (`llm_used`,
запись `llm_fallback` при откате).

Каталог `outputs/agent_logs/` содержит 30 журналов детерминированного прогона, каталог
`outputs/agent_logs_llm/` — три выпуска, где порядок инструментов выбирала модель (05.02, 15.02, 21.02).
В выпусках 15.02 и 21.02 модель самостоятельно распознала обновление входных данных и вызвала пересчёт,
трасса такая:

```
get_weather → check_input_quality → prepare_and_predict → analyze → prepare_and_predict → recalculate → save_forecast
```

Повторный `prepare_and_predict` в середине — внутренний вызов из `recalculate`, он попадает в трассу
отдельной записью, поэтому по журналу видно и решение, и действие.

## Бюджет LLM

| Вызов | Что уходит в модель | Модель |
|---|---|---|
| Шаг оркестрации | системный промпт + схемы шести инструментов + история диалога с результатами инструментов | дешёвая (`OPENAI_MODEL`, сейчас `gpt-5.4-mini`) |
| Заключение | та же история, ответ 3–5 предложений | та же дешёвая модель; тяжёлая (`OPENAI_REASONING_MODEL`, `gpt-5.4`) зарезервирована на разбор итогов |

Замерено на трёх выпусках с живой оркестрацией (счётчик `app.llm.USAGE`): 17 обращений к API,
13 657 входных и 612 выходных токенов — то есть 5–6 обращений и около 4,5 тысячи входных токенов на
выпуск, история переотправляется на каждом шаге. В пересчёте на 30 выпусков — порядка 140 тысяч входных
токенов, единицы центов по тарифам mini-моделей. Точную сумму смотрите в актуальном прайсе провайдера.

Почему бэктест по умолчанию идёт без LLM (`--no-llm`):

- воспроизводимость: жюри повторяет прогон без ключей, без сети и получает те же числа;
- детерминизм: сравнение выпусков между собой не зашумлено вариативностью модели;
- стоимость и лимиты: 30 выпусков подряд упираются в rate limit, а прогноз от этого не улучшается —
  числа даёт модель выработки, LLM выбирает порядок действий и пишет заключение.

LLM-оркестрация включается флагом `--llm` на одном выпуске или на всём периоде и фиксируется в журнале
полем `llm_used`.
