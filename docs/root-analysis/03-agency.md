# Агентность: что в задаче действительно требует агента

Раздел комиссии по разбору корня кейса. Вопрос: где агентность создаёт измеримую ценность, а где
она декоративна. Все числа получены прогоном на артефактах репозитория, скрипты проверки —
во временной папке сессии, код проекта не менялся.

Источники: `app/agent.py`, `docs/agent-design.md`, 28 журналов `outputs/agent_logs/*.json`,
3 журнала `outputs/agent_logs_llm/*.json`.

## 1. Сколько решений агента изменили результат

**Ноль из двадцати восьми.**

Из 28 выпусков бэктеста 24 прошли по последовательности
`get_weather → prepare_and_predict → analyze → save_forecast`, то есть ровно как жёсткий конвейер.
В 4 выпусках агент дополнительно вызвал `recalculate`:

| Дата | Расхождение с прошлым выпуском | Порог | Штормовых часов | `input_changed` | Обнулено строк |
|---|---|---|---|---|---|
| 2026-02-06 | 0.156 | 0.15 | 0 | False | 0 |
| 2026-02-15 | 0.164 | 0.15 | 0 | False | 0 |
| 2026-02-21 | 0.184 | 0.15 | 0 | False | 0 |
| 2026-02-24 | 0.214 | 0.15 | 0 | False | 0 |

Прямая численная проверка: для каждого из четырёх дней выпуск агента сопоставлен с результатом
конвейера «погода → прогноз → сохранить» без анализа и пересчёта. Максимальное расхождение по всем
колонкам `power_*` — **0.0000000000** во всех четырёх случаях.

Пересчёт — пустая операция. Причин три, и все системные, а не случайные:

1. **Архив суточной гранулярности.** `recalculate` заново вызывает `forecast_available_at`, но для
   прошедшей даты Previous Runs API отдаёт тот же срез; кэш в `data/cache/weather/` возвращает те же
   байты. Обновиться входу неоткуда. Это зафиксировано самим агентом в поле `input_changed: False`.
2. **Модель детерминирована.** Повторный `prepare_and_predict` на тех же входах даёт те же числа.
3. **Штормовая ветка ни разу не сработала.** `storm_hours = 0` во всех 28 выпусках: за февраль 2026
   прогнозный ветер на 100 м ни разу не достиг порога 22 м/с. Единственный механизм, который мог бы
   изменить числа при пересчёте, на тестовом периоде не активировался ни разу.

Побочная находка. Детектор обновления работает только когда вчерашний выпуск передан явно
(`previous=`). Если положиться на чтение с диска (`app/agent.py:167–170`) и файла нет — расхождение
не считается, `needs_recalculation` всегда False. В бэктесте выпуск передаётся, в одиночном вызове
`app.cli forecast --date` — зависит от наличия вчерашнего файла.

## 2. LLM против детерминированного плана

Сравнение на трёх датах, где есть оба журнала:

| Дата | Трасса совпадает | Анализ совпадает | Решение о пересчёте | Что отличается |
|---|---|---|---|---|
| 2026-02-05 | да | да | оба: нет | только текст заключения |
| 2026-02-15 | да | да | оба: да | формулировка причины, текст заключения |
| 2026-02-21 | да | да | оба: да | формулировка причины, текст заключения |

Ни на одной дате модель не приняла решения, которого не принял бы детерминированный планировщик.
Порядок инструментов совпал посимвольно, включая повторный `prepare_and_predict` внутри
`recalculate`.

Единственное содержательное отличие — качество причины пересчёта. Детерминированный план пишет
шаблон «обновление входных данных или штормовые часы», модель пишет
`input_change_vs_previous_issue=0.164 exceeds update_threshold=0.15`, то есть называет конкретный
сработавший критерий. Это польза для разбора инцидента, но не для прогноза.

**Вывод без снисхождения.** На текущем периметре LLM-контур не влияет на числовой результат. Он
даёт: (а) объяснение на естественном языке, (б) устойчивость к тому, что состав инструментов
изменится без переписывания планировщика. Называть это «агент принимает решения» — преувеличение:
решение одно, оно сводится к сравнению числа с порогом, и его принимает `analyze`, а не модель.
Модель лишь исполняет то, что ей продиктовано полем `needs_recalculation`.

## 3. Где агентность была бы настоящей

Критерий: решение требует агента, если пространство вариантов не сводится к одному порогу, а цена
ошибки выбора выше стоимости вызова модели.

| Решение | Нужна ли LLM | Чем измерить пользу | Есть ли у нас |
|---|---|---|---|
| Деградация источника погоды: одна модель не ответила или отдала мусор — взять другую, смешать оставшиеся, отложить выпуск | Нет, достаточно правил и проверок качества | Доля выпусков, состоявшихся при отказе источника; ошибка на таких выпусках | Нет: источник один, запасного нет |
| Аномалия входа: пропуски, застрявший датчик, физически невозможные значения, обрезанный ряд | Нет, правила. LLM — только для формулировки инцидента | Доля пойманных подмен в контролируемом эксперименте | **Нет, и это главный пробел** — см. раздел 4 |
| Существенное обновление прогноза → пересчёт | Нет, один порог | Изменение MAE после пересчёта | Есть, но на архиве бессмысленно: вход не обновляется |
| Эскалация диспетчеру при высокой неопределённости | Нет для срабатывания, да для текста сообщения | Доля ложных тревог против пропущенных провалов | Нет |
| Выбор модели или режима при смене сезона, деградации качества | Пограничный случай: правило по скользящей ошибке проще и надёжнее | Ошибка после переключения против ошибки без него | Нет |
| Объяснение расхождения прогноза и факта постфактум | **Да, здесь LLM уместна**: свободный текст по разнородным признакам | Оценка диспетчером; сокращение времени разбора | Нет (факт за февраль недоступен) |
| Сводка выпуска для человека | Да, но это генерация текста, а не агентность | — | Есть |

Честный итог: в этой предметной области почти всё, что называют агентностью, — это правила и
проверки качества данных. LLM объективно нужна в двух местах: объяснение на естественном языке и
устойчивость оркестрации к изменению состава инструментов. Остальное — детерминированная логика,
которую агент обязан исполнять, а не выдумывать.

## 4. Проверяемый критерий агентности: эксперимент с деградацией входа

Проведён контролируемый эксперимент на дате 2026-02-10: в погодный кадр вносится дефект, агент
запускается штатно, смотрим реакцию.

| Дефект входа | Результат выпуска | Пометил ли агент проблему |
|---|---|---|
| Норма (контроль) | средняя 0.345, NaN 0, штиль 15 ч | — |
| 13 часов пропусков (NaN) | средняя 0.244, **26 строк выпуска с NaN** | нет |
| Застрявший датчик (константа) | средняя 0.835, штиль 0 ч | нет |
| Сдвиг +5 м/с | средняя 0.687 | нет |
| Отрицательный ветер | средняя 0.062, штиль 48 ч | нет |
| Обрезанный ряд, 20 часов вместо 48 | средняя 0.482, выпуск на 20 часов | нет |

Ни один дефект не пойман: ошибок в трассе ноль, `needs_recalculation` False, выпуск сохранён и
объявлен состоявшимся во всех шести случаях. При пропусках на диск уходит прогноз с пустыми
значениями мощности, при застрявшем датчике — физически бессмысленный ровный прогноз с КИУМ 0.84,
при обрезанном ряде — неполные сутки под видом полного выпуска.

Это и есть место, где агентность перестаёт быть декоративной: **агент, который не заметил, что
вход испорчен, выпускает вредный прогноз с тем же уверенным заключением, что и исправный**.

Предлагаемый эксперимент для жюри — ровно этот, в виде воспроизводимого теста: шесть деградаций,
две конфигурации (с проверкой качества входа и без), таблица «поймано / пропущено». Жёсткий
конвейер проваливает все шесть, агент с инструментом контроля качества ловит их и либо отказывается
выпускать, либо выпускает с явной пометкой достоверности. Это разный результат при одинаковых
входах — то есть доказательство, а не декларация.

Трудоёмкость: инструмент `check_input_quality` (проверки на пропуски, постоянство, диапазон
0–40 м/с, полноту сетки часов) — около 40 строк; ветка поведения в планировщике и в системном
промпте — 15 строк; тест с шестью деградациями — около 60 строк. Оценка 40–60 минут вместе с
прогоном и обновлением журналов.

## 5. Риски LLM-контура

| Риск | Состояние |
|---|---|
| Недетерминированность результата | Закрыт: числа считают инструменты, модель влияет только на порядок вызовов и текст. Проверено на трёх датах — выпуски совпадают |
| Отказ провайдера, лимиты, отсутствие ключа | Закрыт: откат на детерминированный план, в трассе `llm_fallback`, есть автотест |
| Стоимость | Измерено: 5–6 обращений и около 4 тыс. входных токенов на выпуск. На 28 выпусках это порядка 110 тыс. входных токенов. Поэтому бэктест по умолчанию идёт без LLM |
| Задержка | Не измерена систематически; один выпуск с LLM заметно медленнее детерминированного (сетевые обращения против локального расчёта) |
| Галлюцинация в заключении | **Не закрыт.** Числа в заключение подставляет модель из результатов инструментов, машинной сверки нет. На трёх наблюдаемых датах числа верны, но это наблюдение, а не гарантия |
| Модель пропускает обязательный шаг | Закрыт страховкой в `run_day` (`app/agent.py:269–273`): если `analyze` или `save_forecast` не вызваны, они выполняются принудительно |

Незакрытый риск ровно один — сверка чисел в тексте заключения. Лечится дёшево: сравнивать числа,
извлечённые из заключения, с полями анализа и помечать расхождение в журнале.

## 6. Что делать

**Успеваем до 18:00** (по убыванию отдачи):

1. Инструмент контроля качества входа и ветка поведения при дефекте — снимает главный содержательный
   упрёк и даёт жюри воспроизводимое доказательство агентности. 40–60 минут.
2. Тест на шесть деградаций в `tests/` — фиксирует поведение и не даёт ему сломаться. Входит в п. 1.
3. Честная формулировка в `docs/agent-design.md` и README: на архивном периоде пересчёт не меняет
   чисел, потому что архив не обновляется; механизм рассчитан на промышленный режим с четырьмя
   выпусками прогноза в сутки. Сейчас документация об этом говорит вскользь, а число «пересчёт в
   4 днях» подаётся как достижение. 15 минут.

**Требует нормальной работы:**

- Второй источник погоды и правило переключения при деградации первого.
- Оперативный API прогноза вместо архива: только там пересчёт начинает менять числа.
- Сверка чисел заключения с анализом.
- Эскалация диспетчеру по ширине интервала с оценкой ложных тревог.
- Постфактум-разбор расхождения прогноза и факта — единственное место, где LLM даёт то, чего
  правила не дают.
