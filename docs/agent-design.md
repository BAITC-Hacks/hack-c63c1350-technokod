# Устройство агентного контура

Модуль `app/agent.py`. Здесь описано, что именно делает агент, какими инструментами, по каким порогам
принимает решения и что остаётся в журнале для проверки.

## Почему это агент, а не скрипт

Скрипт выполняет фиксированную цепочку вызовов. Агент здесь отличается тремя свойствами:

1. **Наблюдение и решение.** После расчёта прогноз не отдаётся сразу: инструмент `analyze` измеряет
   состояние выпуска (штиль, номинал, шторм, расхождение турбин, отличие от вчерашнего выпуска) и выдаёт
   вердикт `needs_recalculation`. Решение о пересчёте принимается по этому наблюдению, а не по расписанию.
2. **Действие по результату проверки.** При срабатывании условия агент сам вызывает `recalculate`:
   заново берёт входные данные, пересчитывает прогноз, применяет защитный останов и повторно прогоняет
   анализ — то есть проверяет результат собственного действия.
3. **Выбор порядка действий.** Когда доступна LLM, последовательность инструментов выбирает модель через
   function calling, а не жёсткий код. Набор инструментов при этом один и тот же в обоих режимах, поэтому
   результат остаётся проверяемым.

Цикл одного выпуска:

```
наблюдение            решение                действие              проверка
get_weather ──► prepare_and_predict ──► analyze ──► needs_recalculation?
                                            │              │ да
                                            │              ▼
                                            │        recalculate ──► analyze (повторно)
                                            │ нет          │
                                            ▼              ▼
                                        save_forecast ◄────┘  → CSV выпуска + журнал JSON
```

**Критерии остановки.** Цикл ограничен `max_steps = 10` обменами с моделью. Выпуск считается
состоявшимся только после `save_forecast` (флаг `saved`): если модель закончила без сохранения, это
ошибка, и выпуск переигрывается детерминированным планом. Повторный пересчёт не зацикливается —
`recalculate` вызывает `analyze`, но не сам себя.

## Инструменты

Пороги заданы константами в начале `app/agent.py`: `CALM_MS = 3.0`, `RATED_MS = 11.5`, `STORM_MS = 22.0`,
`UPDATE_THRESHOLD = 0.15`. Пороги скорости ветра согласованы с кривой мощности из `docs/analysis.md`
(нулевая выработка до 3 м/с, полка с 11–12 м/с).

### `get_weather(issue_date?)`

Забирает архивный прогноз на 48 часов по координатам ВЭС, каким он был доступен на дату выпуска
(`forecast_available_at`). Аргумент `issue_date` необязателен, по умолчанию — дата текущего выпуска.

Возвращает: источник, дату выпуска, число часов, границы периода, сколько часов пришло из слоя за сутки
и за двое суток, min/mean/max скорости ветра на 100 м и температуры. Кадр погоды остаётся в состоянии
агента. Пустой архив возвращается как `{"error": ...}`, а не исключение.

### `prepare_and_predict()`

Строит признаки и считает прогноз по каждой турбине моделью из `models/turbine_*.joblib` (модели
кэшируются в процессе: бэктест прогоняет 28 выпусков без повторного чтения с диска).

Возвращает по каждой турбине: число часов, средний КИУМ, суммарную нормированную выработку за горизонт
(`energy_norm_h`, норм·ч), час и значение пика. Без предварительного `get_weather` возвращает ошибку.

### `analyze()`

Считает состояние выпуска:

| Поле | Смысл |
|---|---|
| `calm_hours` | часов с ветром ниже 3 м/с — выработки не будет |
| `rated_hours` | часов с ветром от 11.5 м/с — полка номинальной мощности |
| `storm_hours` | часов с ветром от 22 м/с — риск защитного останова |
| `turbine_spread_max` | максимальное расхождение прогнозов двух турбин в один час |
| `overlap_hours_with_previous` | сколько часов пересекается со вчерашним выпуском (обычно 24) |
| `input_change_vs_previous_issue` | среднее абсолютное изменение прогноза на этих часах |
| `update_detected` | изменение превысило `UPDATE_THRESHOLD = 0.15` |
| `needs_recalculation` | `storm_hours > 0` или `update_detected` |
| `mean_cf` | средний КИУМ по турбинам |
| `verdict` | текстовый вывод для журнала и для модели |

Если предыдущего выпуска нет (первый день периода), поля сравнения пустые, и это честно попадает в
заключение.

### `recalculate(force?, reason?)`

Срабатывает, если анализ потребовал пересчёта либо передан `force`. Иначе возвращает
`{"recalculated": false, "reason": "анализ не выявил …"}` и ничего не меняет — отказ от лишней работы
тоже фиксируется в трассе.

При пересчёте: заново берётся погода на ту же дату выпуска, пересчитывается прогноз, часы с ветром от
22 м/с обнуляются (защитный останов турбины), считается `mean_abs_change` относительно предыдущего
расчёта, затем повторно вызывается `analyze`.

### `save_forecast()`

Пишет `outputs/forecasts/<issue_date>.csv` (96 строк, колонки `FORECAST_COLUMNS`) и журнал
`outputs/agent_logs/<issue_date>.json`, возвращает пути и число строк. Заключение дописывается в журнал
в конце выпуска, когда оно готово.

## Оркестрация моделью

Схемы инструментов — `TOOL_SCHEMAS` в формате OpenAI function calling
(`{"type": "function", "function": {"name", "description", "parameters"}}`). Обмен идёт через
`app.llm.chat_tools`, который возвращает единый словарь `{"content", "tool_calls"}` независимо от версии
SDK, поэтому агент не зависит от формы ответа провайдера.

Системный промпт (`SYSTEM_PROMPT`) задаёт:

- роль: агент-диспетчер ВЭС из двух турбин, Шелекский коридор;
- задачу: выпустить почасовой прогноз на 24–48 часов для названной даты выпуска;
- запрет на фактическую погоду: только `get_weather`, то есть архивный прогноз на дату выпуска;
- обязательный полный цикл и обязательный вызов `save_forecast` — до него прогноз не выпущен;
- правило пересчёта: при штормовых часах или изменении входных данных вызвать `recalculate`;
- формат заключения: 3–5 предложений по-русски, без разметки, для диспетчера.

Обработка ошибок и лимитов: каждый вызов инструмента обёрнут в `try/except`, ошибка возвращается модели
как `{"error": ...}` и не роняет выпуск — модель может исправиться следующим вызовом. Сбой самого
провайдера (нет ключа, сеть, лимит, отказ вызвать инструменты, отсутствие `save_forecast`) перехватывается
в `run_day`: в трассу добавляется `llm_fallback` с типом и текстом ошибки, расчётное состояние
сбрасывается, выпуск переигрывается детерминированным планом.

**Режим без ключа.** `llm.available()` проверяет провайдера и `DEMO_MODE`; при `use_llm=None` агент сам
решает, доступна ли оркестрация. Детерминированный план выполняет те же пять инструментов в фиксированном
порядке, а заключение собирает из тех же чисел анализа (`_plain_narrative`). Поэтому жюри получает
идентичный по структуре результат без ключей и без сети.

## Обнаружение обновления входных данных

Сравниваются пересекающиеся часы соседних выпусков: часы 25–48 вчерашнего выпуска — это часы 1–24
сегодняшнего, и они посчитаны по разным прогнозам погоды (слой за двое суток против слоя за сутки).
Среднее абсолютное изменение прогноза мощности на этих часах — прямая мера того, насколько обновился
вход. Порог 0.15 по нормированной мощности означает смену режима, а не шум уточнения.

Предыдущий выпуск передаётся в `run_day(issue_date, previous=...)`; если не передан, агент читает
вчерашний CSV с диска. Штормовые часы обрабатываются отдельно от порога: при ветре от 22 м/с
соответствующие часы обнуляются, потому что турбина уходит в защитный останов и модель кривой мощности
там неприменима (в обучающей истории таких режимов нет — максимум 23 м/с по датчику гондолы).

## Журнал действий

`outputs/agent_logs/<дата>.json`:

```json
{
  "issue_date": "2026-02-05",
  "llm_used": false,
  "recalculated": false,
  "rows": 96,
  "analysis": { "calm_hours": 8, "rated_hours": 8, "storm_hours": 0, "…": "…" },
  "conclusion": "Выпуск 2026-02-05, горизонт 48 ч. …",
  "trace": [ { "tool": "get_weather", "args": {}, "result": { "…": "…" } } ],
  "paths": { "forecast_csv": "…", "log_json": "…" }
}
```

По журналу проверяется главное требование кейса: в трассе видно, что погода получена инструментом
`get_weather` с указанием источника «прогноз, доступный на дату выпуска», а не из факта; видно, какие
решения принял агент, был ли пересчёт и по какой причине, и вызвал ли оркестратор LLM (`llm_used`,
запись `llm_fallback` при откате).

## Бюджет LLM

| Вызов | Что уходит в модель | Модель |
|---|---|---|
| Шаг оркестрации | системный промпт (~300 токенов) + схемы пяти инструментов (~500) + история диалога с результатами инструментов | дешёвая (`OPENAI_MODEL`, по умолчанию `gpt-4.1-mini`) |
| Заключение | та же история, ответ 3–5 предложений | та же дешёвая модель; тяжёлая (`OPENAI_REASONING_MODEL`) зарезервирована на разбор итогов |

Оценка по порядку величины: один выпуск — 5–7 обменов, суммарно примерно 10–15 тысяч входных токенов и
несколько сотен выходных (история переотправляется на каждом шаге). Двадцать восемь выпусков —
порядка 300–400 тысяч входных токенов, то есть единицы центов при тарифах уровня mini-моделей. Точную
сумму смотрите в актуальном прайсе провайдера.

Почему бэктест по умолчанию идёт без LLM (`--no-llm`):

- воспроизводимость: жюри повторяет прогон без ключей, без сети и получает те же числа;
- детерминизм: сравнение выпусков между собой не зашумлено вариативностью модели;
- стоимость и лимиты: 28 выпусков подряд упираются в rate limit, а прогноз от этого не улучшается —
  числа даёт модель выработки, LLM выбирает порядок действий и пишет заключение.

LLM-оркестрация включается флагом `--llm` на одном выпуске или на всём периоде и фиксируется в журнале
полем `llm_used`.
