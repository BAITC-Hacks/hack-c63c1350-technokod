### README (пункт с самым высоким риском недопуска)

5.4.15: «Для прохождения технической проверки Проект должен быть подготовлен к самостоятельному запуску и проверке экспертами Организатора. Команда обязана разместить в Репозитории актуальный README-файл, содержащий:

- описание решения и его назначения;
- описание архитектуры;
- используемые технологии;
- инструкции по установке;
- инструкции по запуску;
- необходимые зависимости;
- параметры окружения;
- порядок проверки основного сценария работы.

README-файл должен позволять техническим экспертам понять принцип работы решения и самостоятельно выполнить его развертывание».

5.6.4 повторяет требование и добавляет «системные требования».

5.4.16 и 5.6.5: «Если итоговую версию Проекта не удаётся запустить по инструкциям, размещённым в Репозитории, Команда **не допускается к дальнейшему отбору**. Дополнительные пояснения и исправления не принимаются».

5.6.3: «Материалы Проекта, размещённые в Репозитории, должны позволять Техническим экспертам самостоятельно развернуть, запустить и проверить Проект».

5.6.6: «Команда обязана обеспечить возможность проверки ключевой функциональности Проекта **без необходимости использования личных аккаунтов участников, персональных подписок или закрытых учетных записей**. В случае использования внешних сервисов, API или иных инструментов команда обязана предоставить необходимые демонстрационные доступы, тестовые учетные записи либо иные способы проверки работы решения».

Дополнительно Инструкция (п. 7) перечисляет состав README: что делает проект; что реализовано; используемые технологии и архитектура; порядок установки и запуска; пример проверки; используемые данные и внешние сервисы; известные ограничения; ссылка на развёрнутую версию, если она есть.

### Критерии оценки

Технический отбор идёт по критериям ТЗ кейса (5.5.1–5.5.3: «Техническая оценка каждого Проекта осуществляется в соответствии с требованиями, критериями оценки, правилами начисления баллов… установленными в техническом задании соответствующей Задачи»):

| Критерий ТЗ кейса | Баллы |
|---|---|
| Соответствие задаче и работоспособность | 25 |
| Техническая реализация (подход, архитектура, взаимодействие компонентов, использование AI/agentic AI; соответствие фактической реализации заявленной логике) | 25 |
| README и воспроизводимость (документация + возможность воспроизвести и проверить решение по материалам репозитория) | 25 |
| Ценность и применимость решения | 15 |
| Потенциал развития и оригинальность подхода | 10 |
| **Итого** | **100** |

На Demo Day (5.7.2) действует другая шкала — она применяется только к финалистам: ценность решения 25, результат и качество 20, инновационность 15, потенциал развития и масштабирования 20, презентация, демо и ответы на вопросы 20, итого 100. Пункт 5.7.3: итоговое коллективное решение Жюри имеет приоритет перед арифметическим рейтингом.

### Ключевое содержательное требование кейса

ТЗ: «Для каждого прогнозного периода участники должны использовать **архивные прогнозы погоды, которые были доступны на соответствующий момент времени, а не фактические погодные значения**, ставшие известными позднее». Цикл Agentic AI задан дословно: «получение внешних погодных данных — подготовка данных — запуск модели прогнозирования — формирование почасового прогноза — анализ результата — повторный расчёт при обновлении входных данных». Период: прогноз на 31 января, затем на 1 февраля и далее последовательно до конца февраля 2026.

### Дисквалификация (5.9.2), что касается нас напрямую

- «отсутствие у команды подтверждённого промежуточного результата по итогам **любого отчётного часа** соревновательной части» (требование 5.4.8: каждый час — коммит, прототип, схема, настроенная модель, тестирование, подготовленные данные и т. п.);
- «ведение основной разработки Проекта вне GitHub-репозитория команды… либо отсутствие в нём подтверждаемой истории разработки»;
- представление проекта, преимущественно созданного третьими лицами, без раскрытия;
- отсутствие участника на площадке в период обязательного присутствия, непрохождение check-in.

Пункт 5.4.12.1: использование внешних API и облачных сервисов допускается «при условии обязательного личного присутствия Участников на площадке Хакатона в период Соревновательной части».

## 4. Риски по убыванию

1. **Незаполненная форма «Сдать решение»** — проект в репозитории есть, но формально не подан. Устраняется только капитаном.
2. **Запуск по README на чужой машине** (5.4.16 — недопуск без права на исправление). Нужен прогон с чистого клона по тексту README, а не по памяти.
3. **Расхождение README с фактической реализацией** (критерий «Техническая реализация» прямо требует «соответствия фактической реализации заявленной логике проекта», 25 баллов) — все числа и утверждения README должны совпадать с кодом и `docs/metrics.json`.
4. **Часовой промежуточный результат** (5.4.8, основание для дисквалификации) — не оставлять часовых окон без коммита до 18:00.
