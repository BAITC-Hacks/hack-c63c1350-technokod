# Регламент эксплуатации

Документ для дежурной смены и инженера сопровождения: когда выпускать прогноз, как развернуть, что смотреть каждый день, что делать при отказах.

Установка и разбор команд — в [user-guide.md](user-guide.md). Здесь только эксплуатация.

## Регламент выпусков

Глобальные модели погоды, на которых стоит Open-Meteo, обновляются четыре раза в сутки (прогоны 00, 06, 12, 18 UTC), данные становятся доступны примерно через 4 часа после начала прогона. Алматы — UTC+5.

| Выпуск | Местное время | Что закрывает | Действие |
|---|---|---|---|
| Основной | 05:40 | сутки D+1 полностью и сутки D+2 | обязательный выпуск, идёт в заявку на рынок |
| Уточняющий | 11:40 | остаток D+1 и D+2 | пересчёт при изменении входных данных |
| Уточняющий | 17:40 | остаток D+1 и D+2 | пересчёт при изменении входных данных |
| Ночной | 23:40 | сутки D+1 | контрольный прогон перед утренним выпуском |

Решение о пересчёте принимает агент: инструмент `analyze` сравнивает новый прогноз с предыдущим выпуском на пересекающихся часах, и при среднем изменении больше 0.15 по нормированной мощности либо при появлении часов со скоростью ветра ≥ 22 м/с вызывается `recalculate`. Штормовые часы обнуляются как защитный останов. Факт пересчёта виден в журнале выпуска (`recalculated: true`) и в строке `outputs/backtest_summary.csv`.

Ограничение текущей реализации: выпуск привязан к дате, а не к конкретному прогону модели погоды, потому что источником служит архив прогнозов (`previous-runs-api.open-meteo.com`). Для промышленного контура с четырьмя выпусками в сутки нужен вызов оперативного API прогноза (`api.open-meteo.com/v1/forecast`) — в коде его сейчас нет, это работа на внедрение.

## Развёртывание

### Локально

```bash
git clone <репозиторий> /opt/windagent && cd /opt/windagent
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env            # ключ LLM не обязателен
.venv/bin/python -m app.cli check
.venv/bin/python -m app.cli train
```

Каталоги, которые должны переживать перезапуск: `models/` (обученные модели), `outputs/` (выпуски и журналы), `data/cache/weather/` (кэш прогнозов).

### Docker

```bash
docker compose build
docker compose run --rm app python -m app.cli check
docker compose run --rm app python -m app.cli train
docker compose run --rm app python -m app.cli forecast --date 2026-02-10 --no-llm
```

Файл `.env` обязателен, его требует `docker-compose.yml`; допустимо создать его из `.env.example` с пустым ключом. В текущем `docker-compose.yml` пробрасывается только `./data`, поэтому модели и результаты остаются внутри контейнера — при развёртывании добавьте тома:

```yaml
volumes:
  - ./data:/app/data
  - ./models:/app/models
  - ./outputs:/app/outputs
```

### По расписанию

Linux, cron (четыре выпуска в сутки, запись в журнал):

```cron
40 5,11,17,23 * * * cd /opt/windagent && .venv/bin/python -m app.cli forecast --date $(date +\%F) >> logs/agent.log 2>&1
30 3 1 * *          cd /opt/windagent && .venv/bin/python -m app.cli train >> logs/train.log 2>&1
```

Windows, планировщик задач. Обёртка `run_forecast.ps1` в корне проекта:

```powershell
Set-Location $PSScriptRoot
$date = Get-Date -Format "yyyy-MM-dd"
.venv\Scripts\python.exe -m app.cli forecast --date $date *>> logs\agent.log
```

Регистрация задачи:

```powershell
schtasks /Create /TN "WindAgent forecast" /SC DAILY /ST 05:40 /RI 360 /DU 24:00 ^
  /TR "powershell -NoProfile -ExecutionPolicy Bypass -File C:\windagent\run_forecast.ps1"
```

`/RI 360` повторяет задачу каждые 6 часов, то есть даёт те же четыре выпуска в сутки.

## Ежедневный контроль

| Что смотреть | Где взять | Норма |
|---|---|---|
| Выпуск состоялся | `outputs/forecasts/<дата>.csv`, 96 строк | файл за сегодняшнюю дату есть |
| Полный цикл агента | `outputs/agent_logs/<дата>.json`, ключ `trace` | присутствуют `get_weather`, `prepare_and_predict`, `analyze`, `save_forecast` |
| Число пересчётов | `recalculated` в журнале, `recomputed` в сводке | единичные случаи; каждый день подряд — повод разобраться с источником погоды |
| Доля часов с данными | `hours` в сводке выпуска | 48 часов на выпуск, 96 строк на две турбины |
| Работа LLM | `llm_used` в журнале, наличие `llm_fallback` в трассе | откаты единичны; постоянный `llm_fallback` — проблема с ключом, лимитом или сетью |
| Свежесть кэша погоды | время изменения файлов в `data/cache/weather/` | появляются новые файлы в дни выпусков |
| Ошибка последних 7 суток | сравнение `outputs/forecast_all_issues.csv` с фактом выработки после его поступления | MAE того же порядка, что на валидации: около 0.15 на горизонте 24 ч |
| Эталон качества | `docs/metrics.json`, раздел `honest_jan2026` | ориентир для сравнения: nMAE ≈ 14.6–14.7 % на 24 ч, ≈ 16.8–16.9 % на 48 ч |

Сводку по уже посчитанному даёт `python -m app.cli report`.

## Отказы и реакция

| Симптом | Причина | Действие |
|---|---|---|
| `архив прогнозов пуст`, ошибки `httpx` | Open-Meteo недоступен или нет сети | повторить выпуск через 15–30 минут; при длительном отказе выпуск идёт по последнему кэшу, в журнале отметить, что входные данные не обновлялись |
| В трассе всегда `llm_fallback` | нет ключа, исчерпан лимит OpenAI, неверный провайдер | проверить `check`, продлить лимит; прогноз при этом продолжает выпускаться детерминированным планом, срочности нет |
| `Модели не обучены` | потерян каталог `models/` | выполнить `train`, около 4 минут |
| Модели старше месяца | пропущено плановое переобучение | запустить переобучение по разделу ниже |
| Пропал факт по одной турбине | обрыв связи с терминалом ВЭС | прогноз продолжает выпускаться (факт в прогнозе не участвует), но обучение на этом периоде будет с пропусками; восстановить выгрузку до следующего переобучения |
| Прогноз «залип» на полке номинала | прогнозная скорость ветра устойчиво выше 11.5 м/с, либо испорчены входные данные | сверить `wind_speed_100m` в файле выпуска с независимым источником; при расхождении очистить соответствующие файлы кэша и повторить выпуск |
| Аномальный ветер (≥ 22 м/с) | штормовой прогноз | агент обнуляет эти часы как защитный останов; смене сообщить о риске останова, проверить фактический регламент станции |
| Разброс между турбинами резко вырос | деградация одной из моделей или изменение состояния турбины | сравнить `turbine_spread_max` в журналах за неделю, при устойчивом росте переобучить модели |

## Переобучение

Плановое — раз в месяц, после закрытия месяца по факту выработки. Внеплановое — если недельная ошибка по факту устойчиво в полтора раза выше валидационной.

Порядок:

1. Сохранить текущие модели и метрики: `cp models/turbine_1.joblib models/turbine_1.joblib.bak` (аналогично для второй турбины), `cp docs/metrics.json docs/metrics.json.bak`.
2. Прогреть кэш на новый период: `python -m app.cli fetch-weather --start <начало> --end <конец>`.
3. Запустить `python -m app.cli train`. Обучение идёт на истории выработки и архивных прогнозах, валидация — тот же протокол «прогноз как в прошлом».
4. Сравнить новый `docs/metrics.json` с сохранённой копией по разделу `honest_jan2026`: MAE на горизонтах 24 и 48 часов не должен вырасти.
5. Если качество упало — откат: вернуть `.bak` на место, разобраться с данными за новый период.

Валидационный период при сравнении менять нельзя, иначе числа несопоставимы.

## Секреты и данные

- Ключи только в `.env` и переменных окружения. Файл в `.gitignore`, в репозиторий не попадает.
- В журналы агента и в выходные CSV ключи не пишутся: трасса содержит имена инструментов, их аргументы и числовые результаты.
- Кэш `data/cache/weather/` содержит только погодные данные Open-Meteo и передаётся свободно.
- Данные выработки — собственность станции; порядок их публикации определяет владелец.
- При обращении в поддержку прикладывайте `outputs/agent_logs/<дата>.json` и вывод `check` — секретов там нет.

## Резервный сценарий

Полностью автономный режим: без сети и без ключа LLM.

```powershell
.venv\Scripts\python.exe -m app.cli forecast --date 2026-02-10 --no-llm
```

Работает при условии, что модели обучены и нужные даты есть в кэше погоды. Что теряется: порядок вызова инструментов выбирает не модель, а детерминированный планировщик, и заключение для диспетчера формируется шаблоном по числам анализа, а не текстом модели. Сам прогноз, анализ, детектор обновления и пересчёт работают одинаково в обоих режимах — числовой результат от наличия LLM не зависит.
